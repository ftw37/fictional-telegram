# Rendering slowdown investigation

October 24 measurement tools align route events, FPS windows and GPU-profile frames using Unix timestamps. `--frame-stats` retains lightweight five-second windows. `--profile-cpu` adds two-second windows and CPU call scopes without GPU timestamp captures. `--profile-render` additionally serializes one GPU frame every fifteen seconds and groups its work by target and shader.

CPU scopes are nested: buffer/texture scopes sit inside binding; some driver scopes sit inside other scopes. Do not add them together. The CPU/driver log label explicitly warns of overlap. Translation CPU time comes from the render thread's OS CPU accounting. GPU timestamps include gaps between work, which can include CPU starvation and not just GPU barrier execution. Timestamped captures perturb the frame, so the report excludes overlapping FPS windows using capture start/end markers.

`scripts/render_profile_report.py RUN_FOLDER` produces a private `render-profile.json` with aligned stages, raw windows, scope timings and GPU-frame summaries. Legacy logs without absolute timestamps are not silently assigned to route stages. `tests/test_render_profile_report.py` checks alignment, partial windows, legacy handling and capture overlap. Manual scene markers are observed view samples, not exact scene-onset events; clock alignment does not turn a delayed human observation into an exact onset marker.

The representative broad-barrier profile found about 5,500–5,900 draws per slow frame, versus roughly 1,080 in the sampled faster first-car view. A captured bright-transition frame contained about 2,350 depth-only draws and 2,800 draws into the main six-target scene output. This establishes substantial depth/main-scene work rather than merely a large postprocessing effect. It does not identify the responsible game objects by name.

In the refined profile, selected slow windows spent roughly 24–28 ms in buffer binding, 7–8 ms in texture binding, and around 5 ms in the inclusive broad-dependency scope. The sampled faster view spent about 1.7 ms in buffer binding. Profiling overhead and dynamically changing scene workloads mean these are diagnostic measurements, not production FPS improvement claims.

The first candidate checked clean CPU-upload ranges before building a temporary bit mask, preserving page-protection updates and all GPU synchronization. Its first test showed no clear FPS gain. The off/on/off experiment also observed a stationary view change from around 5,700 draws to fewer than 500 and 60 FPS, invalidating a simple timing comparison across the last period. The candidate remains diagnostic and disabled by default.

The next candidate measures `FindImageFromRange`. Its selection requires an image's start address to equal the buffer address, yet the previous traversal visits every page of the buffer range. Every qualifying image is registered on the first page already. The diagnostic first-page path preserves candidate order, validity checks and the original requested-size selection; it retains the old traversal for overflowing ranges and returns no match for an empty range. Randomized page-index tests compare full traversal and the restricted traversal against an independent exact-address oracle. Live acceptance results must be recorded separately before enabling it normally.

Build46b's two CPU-only comparison attempts both failed during startup at approximately 124.4 seconds, before player discovery or the first candidate activation. Both logged a guest read access violation at `libc.prx + 0x1ee34`, reading `0xffffffffffffffff`. This establishes neither a first-page optimization failure nor its safety: it never ran. The test is incomplete and the candidate remains off. Further automatic retries were stopped after the second failure. The saved pre-profiling build42 was restored to the double-click runtime for a separate recovery check. The diagnostic build is preserved separately as `source-build46b-profiling-experimental.exe`; rebuilding the current patch produces the diagnostic code, not the restored build42 binary.

Private run folders contain logs with shader hashes, guest addresses and local state. Never commit those logs or captured game assets. Broad barriers and the original limiter remain required during this investigation. The first profiled traversal timed out at a carriage connection; subsequent replay code waits until the next entrance door is actually approached, including movement-base boundary changes. Incomplete traversals are not accepted as full route validations.

Validation: build46b compiled and linked successfully. Five report/alignment unit tests and three image-lookup tests passed (16,384 randomized layouts/comparisons). The exported compatibility patch applied to 43 pristine source files at the pinned revision and matched the modified working tree. These checks do not replace the missing live candidate validation.

Recovery run `baseline-build42-recovery-1` completed on the restored build42 with lightweight FPS logging only: 114.921 seconds of traversal, 315.640 seconds including startup/discovery. The platform endpoint was visually confirmed and the emulator then closed normally. No claim is made that one successful recovery run fixes the diagnostic startup fault or the existing station rendering defects.
